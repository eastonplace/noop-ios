## Source locations and existing ownership

The smallest confirmed app repair is the Settings Done toolbar: main installs it only on `SettingsView` inside `SettingsSheetHost`. `SettingsDetailHost` presents the pushed content without that toolbar. PR #66's existing commits `d9d208d7` and `a7d445f6` introduce/reuse `SettingsSheetDoneToolbar` on pushed and nested pages. The toolbar reads the host's existing close action and preserves native Back navigation. This is already owned by the open UI lane; duplicating it into #71 would introduce overlap without providing additional native evidence.

## Handoff and remaining evidence

1. Keep #71's UI result separate from the already-red main baseline. Wait for its exact-head native result and report it accurately; do not mark UI qualification complete from build/unit-test success.
2. Let the #66/#67 lane validate its final heads with the required full native suite. This report does not recommend merging, cherry-picking UI work, weakening checks, or accepting baseline exceptions.
3. If Lift still fails, inspect the screenshot and accessibility hierarchy immediately after `Pick a routine`, before any scrolling. Determine whether the routines list actually opened, whether `Upper A` exists, and whether asynchronous fixture/root replacement changed the presentation. The current baseline trace cannot distinguish those causes.
4. For any remaining dashboard or typed-destination failure, inspect the saved failure screenshot/hierarchy together with the target and actual scroll-surface frames. For the Breathe switch, inspect the pre/post native and row values plus the synthesized event before proposing a storage fix. The baseline already retains `approved-dashboard-failure-*`, `typed-notification-failure-*`, `notifications-failure-*`, and `failure-accessibility-hierarchy`/`failure-screen` attachments for those suites.
