## Resolved review finding

### R1 — P1: an event-only runner initially treated steady, valid WHOOP HR as a dead stream

**Initial execution chain:** `BLEManager.parseStandardHR` accepted plausible standard 0x2A37 readings, but assigned `LiveState.heartRate` only when its integer value changed. `FrameRouter` similarly suppressed unchanged proprietary HR assignments. The first proposed runner fix subscribed to `$heartRate`, removed timer-fed cached readings, and expected every valid sample to produce a publication. A constant 141 bpm stream therefore stopped producing events even while notifications continued. `LiveSessionEngine.staleAfterSec` is eight seconds: after that interval the runner would falsely go stale, stop coaching/accrual, and eventually auto-end a healthy session. This especially matters for WHOOP 5/MG's standard-HR path. The initial test assigned the published property directly and bypassed the production suppression gate.

**Final resolution reviewed:** `LiveState` now has a non-replaying, non-`@Published` `heartRateArrivals` subject. WHOOP standard HR and the proprietary frame router emit each accepted arrival separately from the deduplicated display snapshot. The other existing live writers—StandardHRSource, HuamiHRSource, FTMSSource and OuraLiveSource—and the explicit QA feed emit the same event after their existing assignments. The runner subscribes to this event and passes its BPM directly to the real engine. Timer ticks pass `nil`. Starting a session does not replay a pre-session display value. Existing display publication behavior, plausibility gates, collection, and persistence remain unchanged. FrameRouter's sleep diagnostic retains its prior changed-value gate.

**Regression coverage reviewed:** the updated native `LiveSessionFreshnessTests` cover cached-value rejection; timer-only staleness; actual `parseStandardHR` intake into a runner; 31 equal-valued standard notifications through a real engine over 30 simulated seconds followed by silence; a single display publication for that steady stream; and repeated proprietary frame arrivals. A subsequent portable harness compiles the exact original/current standard-HR method bodies plus the complete production standard parser and session engine. Its 376 checks reproduce both fabricated timer freshness and the first proposed fix's steady-HR starvation, then show correct arrivals and eventual silence staleness for WHOOP 4 and 5/MG. Apple publication and collector boundaries are explicit synchronous test seams. The revised native tests still require Xcode execution; neither portable harness proves Combine or complete app integration.

**Status:** resolved in source; no dependency on an unmerged PR is needed for the arrival channel. The initially suggested relationship to PR68 was checked and corrected: PR68's emitted-value consumption does not remove these upstream publication gates.

## Verification assessed

Results produced by the implementing agents are evidence reviewed here, not tests this reviewer independently re-executed.

- **Broadcast preference persistence:** the complete production `PuffinExperiment.swift` compiled with real Linux Foundation/CoreFoundation and passed 12 checks for absence, registered defaults, true/false persistence, malformed types and a saved false overriding a registered true. This does not execute AppStorage or a physical firmware write.
- **Live HR arrivals:** the exact standard-HR method/real parser/real engine harness passed 376 checks, with the Apple-facing seams described above. Logs separately demonstrate 31 fixed arrivals versus one display publication, both supported family values, rejection of malformed/out-of-range inputs, accepted boundary values, cached-value nonreplay and silence staleness.
- **Selected analytics sources:** the latest post-HRV-buffer harness passed 192 tests with zero failures. It compiles actual source/test files selected into a Linux-compatible package; it is not the complete StrandAnalytics/WhoopStore app graph.
- **HRV semantic equivalence:** the optimized comparison log records 37,555 fixtures with zero mismatches in exact Double bit patterns, cleaner outputs, gap flags and result counts/statistics. This includes short exhaustive cases, malformed/nonfinite values and an eight-hour synthetic RR stream. The small Linux timing reduction is not a phone or strap battery measurement.
- **Widget reads:** the original and current helper bodies were compiled with the production HR/RR read methods, RR selection policy and analytics, using an explicit SQLite adapter in place of GRDB. The original failed the dense-midnight and 25-hour-day cases; the fixed helper passed all five groups, including the 50 ms noon RMSSD, 90,000 HR seconds, equal RR at the final second, measured-first/source ordering, one WHOOP 5 whole-day transport and eight invalid-bound cases.
